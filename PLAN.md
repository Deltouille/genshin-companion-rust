# Genshin Companion: plan

A Genshin Impact desktop app in Rust + GPUI (Windows, macOS, Linux), formerly Genshin Wishes. It began as a rewrite
of [paimon.moe](https://paimon.moe)'s **wish counter**, whose goal is that wish history is never lost, and now also
has a character archive and an ascension planner.

The original source is cloned locally in `reference/` (git-ignored) as a reference.

## Why paimon.moe loses data

| Problem in paimon.moe | Where | Fix here |
|---|---|---|
| Everything lives in browser IndexedDB (localforage). Clearing site data or switching browser profile wipes it. Google Drive sync uploads the whole save from whichever browser wrote last. | `src/stores/saveManager.js` | SQLite file in the OS data folder, versioned backups, optional mirror folder |
| HoYoverse's API only returns about 6 months of history, so older wishes exist only in the local copy | (game API) | Imports only ever add rows; backups and exports in an open format |
| Imports dedup by timestamp. "Force update" drops every local pull newer than the oldest one the API returns. Computed `pity`/`rate` values are stored inside each pull. | `src/routes/wish/import.svelte` (`getLog`, `processWishes`) | Dedup on the API's unique `id`; computed values are never stored |
| Any item name missing from its built-in list makes `weapons.find(...).id` throw, aborting the import | `import.svelte` (`getLog`) | Store the API's `name` and `rank_type`. Unknown items degrade to "no icon"; the import never fails. |
| Imports go through paimon's own server (`/corsproxy`) | `import.svelte` | The app calls HoYoverse directly |

## Key decisions

| Topic | Decision |
|---|---|
| Source of truth | SQLite (`rusqlite`, bundled) at `directories::ProjectDirs` data dir, transactions for every write |
| Identity | API wish `id` is the primary key; imports use `INSERT … ON CONFLICT DO NOTHING`, so re-importing is always safe |
| Computed values | Pity, banner, 50/50 are recomputed from raw rows on load; never persisted |
| Backups | SQLite online backup to `backups/` before every import, migration or bulk edit, plus daily; keep the last 30 |
| Sync | Optional mirror folder: a lossless JSON snapshot (`snapshot.rs`, own format) written atomically after every change, to a folder synced by the user's own tool. The `.db` never goes in a synced folder. UIGF can't be this format: it requires numeric API ids and HoYoverse item ids, which migrated paimon.moe wishes don't have. |
| Archive | Every imported file is kept as received under `imports/`, so data the app doesn't model yet is never thrown away |
| Undo | Every row (wish, game-id link, manual counter) records the `import_id` that added it, so a whole import can be undone (after a backup). The import stays in the log, marked undone |
| Unknown items | Rarity comes from the API's `rank_type`, not the item list |
| Network | `ureq` (blocking, rustls) on GPUI's background executor; no tokio, no proxy |
| UI | `gpui-kit` (pins GPUI and re-exports `gpui-component`: table, virtual list, charts, dialog, notification, select, sidebar, tabs, progress) |

## Data model

The schema is in `crates/wish-core/src/store/schema/001_initial.sql`.

- `accounts(id, label, uid UNIQUE NULL, server)`: paimon.moe profiles can have no UID (manual counting).
- `wishes`, primary key `(account_id, id)`, with `gacha_type, time, seq, name, item_type, rarity, item_key, manual_pity, source, import_id`.
  - `id` is the API id, or `paimon:<pool>:<YYYYMMDDHHMMSS>:<seq>` for migrated wishes (deterministic, so re-imports dedup).
  - `time` is server-local wall clock, as received.
  - `seq` is the position among the pool's same-time wishes (a 10-pull is 0..=9).
  - `manual_pity` is pity typed by hand in paimon's manual mode.
- `manual_counters(account_id, pool, total, pity5, pity4)`: paimon counters edited by hand.
  Only kept when they differ from what the wish list implies.
- `imports`: an audit log, one row per account per import.

## Engine rules (`engine.rs`, a port of `processWishes` in `import.svelte`)

- **Pity pools:** 100 Beginners, 200 Standard, **301 + 400 Character Event (shared pity)**, 302 Weapon, 500 Chronicled.
  5★ cap is 90 (80 for weapons); 4★ cap is 10.
- **Ordering:** by `(time, seq, gacha_type, id)`. The API returns newest first.
- **Pity:** wishes since the previous item of the same rarity, this one included.
  **A 5★ does not reset the 4★ count**, as in the game and in paimon.
  Hand-typed manual pity is kept as is.
- **Banner matching:** pull times are server-local wall clock. `banners.js` times are UTC+8 wall clock.
  For `timezoneDependent` (`timezoneDependentEnd`) banners, subtract `8 - server_offset` hours from start (end).
  Offsets: Asia/TW +8, China +8, America −5, Europe +1. With no server set, Asia is assumed, like paimon.
  The server comes from the API's `region` field, or paimon's `server` key for migrated data.
  - Scanning only moves forward. A wish after the current banner's end goes to the next banner whose window contains it;
    if none does (a gap between banners), it stays on the current one and counts as `outside_banners`.
  - paimon would crash on a rate-up wish before any banner; here it gets no banner and no 50/50.
- **Dual banners need no logic:** paimon's single entry for that period lists both featured 5★.
  `bannersDual` only supplies the second banner's image.
- **50/50:** a 5★ is a rate-up item if it's in the banner's `featured`. Any other 5★ is a loss and makes the next one guaranteed.
  A rate-up 5★ is a win unless it was guaranteed. Same for 4★ with `featuredRare`.
  - Only Character and Weapon Event are tracked, like paimon; Chronicled could follow later.
  - Streaks are computed but not shown anywhere in paimon.
  - Items without a key are matched by name. Unknown ones get no 50/50 and leave the guarantee state alone.
- **Stats** (`stats.rs`, like `_summary.svelte`): shares use the counter total, so manual counters change the denominator.
  Average pity per rarity, 4★ split into characters and weapons, monthly wish counts over all pools.
- **Acceptance test:** `import::paimon_check` compares the engine with the values paimon stored in a save
  (each pull's `pity`/`rate`, and `total`/`legendary`/`rare`/`guaranteed`/`rateoff`).
  Those stored values are what paimon's counter cards and summary display.

## Banner and item data

- `tools/extract-paimon-data.mjs` imports paimon's `banners.js`, `bannersDual.js`, `characters.js` and `weaponList.js`.
  It writes slim JSON (`id`, `name`, `rarity`, kind) to `crates/wish-core/data/`, embedded with `include_str!`.
- A newer copy in the app's data folder overrides the embedded one, so a new banner needs
  `git -C reference pull` and a re-run of the script.
- Unknown names fall back to a slug id (paimon ids are snake_case names) and render without an icon.
- **Icons:** downloaded on first use from paimon.moe and Project Amber (see "Game art" below); none is embedded.
  **Banner art** (133 MB) is loaded from an optional folder, with the banner's `color` plus name as a fallback.

## Imports

1. **paimon.moe JSON** (done in M1): Settings → Export (`paimon-moe-local-data.json`), or the Google Drive save file (same format).
   - Keys are `[<account>-]wish-counter-<type>`; pulls are `{type, id, time, pity, code?, manualInput?}`, with `unknown_3_star` for manual 3★.
   - Rows get `paimon:` ids. A later API import (M4) links them to real ids by matching (pity pool, time, name) as a multiset,
     since a 10-pull can contain the same 3★ twice.
   - Unknown item keys fail the whole import with the list of keys, rather than guessing a rarity.
     Old numeric times are refused with instructions.
2. **From the game** (done in M4; `import/api.rs`, `game_cache.rs`, `api_plan.rs`):
   - **Paste the link** (works for PC, mobile and PlayStation links). It's found inside any pasted text,
     such as a script's output.
   - **Find the link** in the game's web cache: the game's `output_log.txt` names its data folder
     → newest `webCaches/*/Cache/Cache_Data/data_2` → last URL containing `authkey=`.
     - Windows: the log is in `%USERPROFILE%/AppData/LocalLow/miHoYo/Genshin Impact` (CN: `原神`).
     - Linux: the same logs inside Wine/Proton prefixes (`~/.wine`, An Anime Game Launcher incl. Flatpak,
       Steam `compatdata`), with the log's `C:/…` paths resolved through the prefix's `dosdevices`.
     - Or a game folder chosen by the user, remembered in the settings.
   - **API:** `https://public-operation-hk4e-sg.hoyoverse.com/gacha_info/api/getGachaLog`
     (CN: `public-operation-hk4e.mihoyo.com`). The link's own parameters (`authkey`, `region`, `game_biz`…) are kept;
     `lang=en-us`, `gacha_type`, `size=20` and `end_id` are set per request.
     - Querying 301 also returns 400 rows. Paging stops at the first wish already known for that UID
       (stored from the game, or recorded as a link).
     - 0.6 s between requests. On retcode −110 ("visit too frequently") or a network error, retry with doubling pauses.
       −101 means the link expired; −100 means the link was cut or altered.
     - Cancelling stops within 50 ms.
   - **Plan** against what's stored, per pool:
     - a wish newer than everything stored is new;
     - an older one should be a migrated paimon.moe wish with the same time and name, so its game id is recorded
       in `wish_links` and the stored record isn't touched;
     - an older one with no match fills a gap, unless the pool has hand-typed paimon.moe wishes it could repeat:
       then it's held back and reported.
     - A UID with no account yet can go to a new account or to an account without a UID (paimon.moe profiles);
       the one whose history matches is suggested.
   - **Safety:** results are held in memory, previewed ("N new wishes, M matched"), then written in one transaction.
     Cancelling writes nothing. Importing twice adds nothing.
3. **Snapshot** (done in M1): this app's lossless JSON, for the mirror folder, restores and moving machines.
4. **Other formats** (M5): UIGF v4 import/export for interop with other trackers (needs a name → HoYoverse item id table,
   and synthetic numeric ids for migrated wishes), paimon Excel v3 import (`calamine`), Excel/CSV export (`rust_xlsxwriter`).

## Screens

- **Overview:** 5 counter cards (lifetime pulls, primogems ×160, 5★ pity with a guarantee badge, 4★ pity),
  recent 4★/5★ list with rarity filters, summary (counts, %, average pity, 50/50 rate, streaks), monthly primogem chart.
- **History (one per banner type):** virtualized table (name in rarity color, time, pity, 50/50 icon, 10-pull stripes),
  banner separators, sorting and filters, per-banner stats dialog, pity distribution chart.
- **Import:** pick a method, progress (banner, page, count), preview, confirm.
- **Settings:** data folder and mirror folder, list and restore backups, server override, manual-input toggle.
- **Manual mode:** +1 / +10 / −1, "Get 5★/4★" with a searchable item picker, edit and delete rows.

**Dropped:** global rank and wish tally (need paimon's server), Google Drive sync, ads, translations at first
(strings kept in one place). A possible later replacement for rank is a local "luck percentile" from the known pity model.

## Risks

- **GPUI changes often:** the API breaks between releases. `gpui-kit` is pinned exactly; upgrade on purpose.
- **Platform reach:** desktop is the target. GPUI Kit also advertises WebAssembly, which isn't needed now.
  Phone and PlayStation players copy their link and paste it into the desktop app.
- **Game changes:** HoYoverse may change the API or move the cache file. Pasting the URL is the fallback that always works.
- **Data goes stale:** there's a new banner every few weeks. Missing data degrades gracefully but needs a re-run of the script.
- **Game art:** the images belong to HoYoverse. Neither the repository nor the builds hold them: the app downloads
  them from paimon.moe and Project Amber. If those sites go away, images go missing (the app still works).

## Defaults assumed

- Multiple UIDs supported from the start.
- Manual-input mode kept (done in M5 as "counting by hand").
- A mirror folder instead of real cloud sync.
